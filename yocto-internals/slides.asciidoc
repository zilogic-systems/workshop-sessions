== Things To Know

=== Package Groups

 * Poky allows to create special recipes which can build related group
   of packages.

 * Poky has several predefined packagegroups like
   packagegroup-core-boot, package-group-base etc.,

 * It is possible to create custom package group by inheriting
   packagegroup class and providing the list of packages in RDEPENDS

 * The packagegroup-core-eclipse-debug.bb available in
   meta/recipes-core/packagegroups/ is a fair example for a simple
   packagegroup.

[source,shell]
-------
$ cat layers/openembedded-core/meta/recipes-core/\
packagegroups/packagegroup-core-eclipse-debug.bb
-------

=== Extending and Overriding Recipes

 * If already existing recipe has to be just modified for few
   parameters instead of writing the recipe again,

 * Just the newer modifications can be written in recipe file with
   extension '.bbappend' and sticking to file name as same as the main
   recipe.

 * Even if main and appended recipes are placed in different layers,
   bitbake can resolve them.

 * One example we could find is _busybox_%.bbappend_ in
   _meta-poky/recipes-core/busybox_, whose main recipe _busybox_*.bb_ is
   available in _meta/recipes-core/busybox_

[source,shell]
------
$ cat layers/meta-yocto/meta-poky/recipes-core/busybox/busybox_%.bbappend
$ cat layers/openembedded-core/meta/recipes-core/busybox/busybox_*.bb
------

=== Folders Structure for Build

 * The _tmp/work_ is the folder where all the packages are unpacked and
   built.

 * For each package we would find a folder inside target architecture
   folder.

 * In our build the target architecture is _qemuarm64-poky-linux_

 * The package build directory is available in

-------
   qemuarm64-poky-linux/${PN}/${PV}
-------

 * The source is unpacked and patched in

------
   qemuarm64-poky-linux/${PN}/${PV}/sources
------

=== Why Different Folders under `tmp/work`?

[options="header",cols="2,3,3"]
|===
| Folder | Architecture type | What lives here

| `x86_64-linux`
| build host
| `*-native` tools and cross compilers, run on the host
  (e.g. `arm-linux-gnueabi`, `qemu-system-native`)

| `all-poky-linux`
| `all`
| Architecture independent recipes like
scripts and data only (e.g. `ca-certificates`, `update-rc.d`)

| `cortexa57-poky-linux`
| arm64
| Code that depends only on the target CPU (`busybox`, `bash`, `glibc`)

| `qemuarm64-poky-linux`
| arm64
| Machine specific recipes: kernel, bootloader, images
(`linux-yocto`, `core-image-*`)
|===

=== Why does this split matter?

 * Same CPU architecture, different machine: `cortexa57` packages are built once
   and reused.

 * Native and `all` output is shared by every machine in the build directory

 * Same split in the sstate cache and in `tmp/deploy/rpm/` (one package feed
   folder per architecture)

 * So building images for another machine will build only the machine specific
   recipes, re-using all other recipe builds.

[source,sh]
----
$ bitbake -e busybox     | grep ^PACKAGE_ARCH=   # cortexa57
$ bitbake -e linux-yocto | grep ^PACKAGE_ARCH=   # qemuarm64
$ ls tmp/work/cortexa57-poky-linux/busybox/
----

=== Folders for Package Creation

 * The packages are compiled in _build(B)_ directory.

 * The compiled artifacts are installed in _package_ folder, then it
   is analyzed and segregated in _packages-split_ as development, doc
   and debug packages.

 * Metadata for building packages are available in _pkgdata_
   folder.

=== Folders for Build Logs

 * A _temp_ folder inside the package folder would have build logs
   which can be referred on build failures.

 * We can find the details on build steps involved in building the
   package in file _log.task_order_

 * The tasks are specified in the file in the following format:

--------
<timestamp> <task name> (<pid>): <log file name>.<pid>
--------

== Machine

=== Need for Machine Configuration

  * _Machine_ is the target board for which the image is built.

  * The machine related configurations are available in
    conf/machine/{MACHINE}.conf file in a machine specific layer
    called as BSP layer.

  * BSP layer may also have form-factor configurations like display
    resolution, input devices to configure X11 features etc.

  * BSP layer would also have the Linux kernel compilation recipe,
    which would have default configuration for the target board.

=== Sample Machine Configuration

  * A minimal machine configuration file is given below

------
KERNEL_IMAGETYPE = "zImage"
SERIAL_CONSOLES ?= "115200;ttyAMA0 115200;hvc0"
MACHINE_FEATURES = "alsa bluetooth usbgadget"
PREFERRED_PROVIDER_virtual/kernel ?= "linux-yocto"
PREFERRED_VERSION_linux-yocto ?= "3.19%"
------

 * We can find a sample machine configuration file in
   _layers/openembedded-core/meta/conf/machine/qemuarm64.conf_

== Shared State Cache

=== How State Cache is used?

 * Each task gets a _signature_ (a hash) computed from its inputs:
   recipe, variables, and the tasks it depends on.

 * _Same signature as before:_ the saved output is restored.

 * _Signature changed:_ the task runs again and the new output is saved.


=== Setscene tasks

--------
signature matches    ->  do_<task>_setscene  (restore from sstate-cache)
signature differs    ->  do_<task>           (run the task)
--------

 * The build log shows many _*_setscene_ tasks, these are restores from
   the cache.

 * Since the work was restored, the source is not even unpacked, hence no
   configure or compile tasks are executed.

[source,shell]
-----
ls build/tmp/work/qemuarm64-poky-linux/packagegroup-core-boot/1.0/
-----

=== Advantage of State Cache

 * First build the packages as rpm, then rebuild them as deb.

--------
PACKAGE_CLASSES = "package_deb"
--------

 * Everything up to packaging is restored from the cache.

 * Only the deb packaging task runs again.
